ООП на примере пиццерии

Одна история от начала до конца: заказы пиццы. Никаких котов, машин и телевизоров — только Order и два его вида.

  • Герой: Order — заказ: пицца, адрес, статус
  • Родня: DeliveryOrder — с доставкой, PickupOrder — с самовывозом
  • Правило: текст, код и схема на каждом слайде — про одно и то же
начало · данные вразброс

Зачем собирать данные вместе?

Два заказа — уже шесть переменных, связанных только цифрой в названии: pizza1, address1, status1, pizza2... Какой адрес у первого заказа? Ищи глазами.

# данные вразброс:
pizza1 = 'Маргарита'; address1 = 'Ленина 5'; status1 = 'готовится'
pizza2 = 'Пепперони'; address2 = 'Мира 12'; status2 = 'готовится'
Честно: аккуратный код можно писать и без ООП — например, со словарями и функциями. Объекты — просто удобный способ держать всё, что относится к заказу, в одном месте.
Слева — шесть переменных и вопрос «что к чему». Справа — карточка заказа: всё его — внутри.
понятие · объект

Объект — карточка заказа

Объект — это конкретная карточка: вот этот заказ, с этой пиццей и этим статусом. У карточки есть данные (что помнит) и действия (что умеет).

class Order:
    def __init__(self, pizza, address):
        self.pizza = pizza
        self.address = address
        self.status = 'готовится'

    def mark_ready(self):
        self.status = 'готов'

order1 = Order('Маргарита', 'Ленина 5')
Верх — «что помнит» этот заказ, низ — «что умеет». Это и есть объект order1.
понятие · класс

Класс — бланк заказа

Order — это бланк: описание, какие поля и действия есть у любого заказа. А order1 и order2 — два заполненных бланка со своими данными.

class Order:
    def __init__(self, pizza, address):
        self.pizza = pizza
        self.address = address
        self.status = 'готовится'

    def mark_ready(self):
        self.status = 'готов'

order1 = Order('Маргарита', 'Ленина 5')
order2 = Order('Пепперони', 'Мира 12')
Бланк один — карточек много. Устройство общее, данные у каждой свои.
польза · свой и чужой

Меняешь один — второй цел

Вызываем order1.mark_ready() — готовым становится только первый заказ. Слово self внутри означает «эта самая карточка»: у order1 это order1, у order2 — order2.

class Order:
    def __init__(self, pizza, address):
        self.pizza = pizza
        self.address = address
        self.status = 'готовится'

    def mark_ready(self):
        self.status = 'готов'

order1 = Order('Маргарита', 'Ленина 5')
order2 = Order('Пепперони', 'Мира 12')

order1.mark_ready()  # готов только первый!
print(order1.status)  # готов
print(order2.status)  # готовится
Кнопка — иллюстрация к коду слева: показывает, что меняет вызов order1.mark_ready().
принцип 1 · наследование

Два вида заказов — одна основа

Заказ с доставкой и заказ с самовывозом — оба заказы: у каждого есть пицца, адрес и статус. Поэтому общее описание держим один раз — в Order.

  • Order — что есть у всех: пицца, адрес, статус, mark_ready(), общий ответ how_to_receive()
  • DeliveryOrder — плюс courier и свой ответ how_to_receive()
  • PickupOrder — плюс свой ответ how_to_receive()
Общее живёт в Order. У каждого вида — только его отличия.
принцип 1 · наследование · основа

Сначала — общая основа

Всё, что есть у любого заказа, описываем один раз в Order — включая вопрос how_to_receive() с ответом по умолчанию.

class Order:
    def __init__(self, pizza, address):
        self.pizza = pizza
        self.address = address
        self.status = 'готовится'

    def mark_ready(self):
        self.status = 'готов'

    def how_to_receive(self):
        return 'Способ получения уточняйте'
Основа готова: статус, отметка о готовности и вопрос «как получить» — всё в одном месте. Наследники добавят только своё.
Всё общее — здесь один раз. На следующем слайде наследники добавят только своё.
принцип 1 · наследование · наследники

Наследники: только своё

Запись DeliveryOrder(Order) значит: «возьми всё описание из Order и добавь своё». Статус и mark_ready() писать заново не надо, а how_to_receive() каждый вид задаёт по-своему — это называется переопределением. Строка super().__init__(...) вызывает настройку полей из Order, поэтому pizza, address и status тоже не дублируем.

# продолжение: класс Order — на прошлом слайде
class DeliveryOrder(Order):
    def __init__(self, pizza, address, courier):
        super().__init__(pizza, address)
        self.courier = courier

    def how_to_receive(self):
        return f'Курьер {self.courier} везёт заказ'

class PickupOrder(Order):
    def how_to_receive(self):
        return 'Заберите заказ в пиццерии'
Выгода: исправил mark_ready() один раз в Order — починилось сразу у обоих видов заказов. Общее описание живёт в одном месте.
Серым — то, что досталось от Order даром. Зелёным — своё у каждого вида. Значок ↷ — метод переопределён: название общее, ответ свой.
принцип 2 · полиморфизм

Полиморфизм: один вопрос

Спрашиваем у обоих заказов одно и то же — how_to_receive(), «как получить?». А отвечают они по-разному: у каждого свой способ. Ответ по умолчанию задан в Order, наследники его переопределили — это было на двух прошлых слайдах.

# продолжение: классы — на двух прошлых слайдах
orders = [
    DeliveryOrder('Маргарита', 'Ленина 5', 'Айбек'),
    PickupOrder('Пепперони', 'Мира 12'),
]

for order in orders:
    print(order.how_to_receive())
# Курьер Айбек везёт заказ
# Заберите заказ в пиццерии
# весь пример — можно скопировать и запустить
class Order:
    def __init__(self, pizza, address):
        self.pizza = pizza
        self.address = address
        self.status = 'готовится'

    def mark_ready(self):
        self.status = 'готов'

    def how_to_receive(self):
        return 'Способ получения уточняйте'

class DeliveryOrder(Order):
    def __init__(self, pizza, address, courier):
        super().__init__(pizza, address)
        self.courier = courier

    def how_to_receive(self):
        return f'Курьер {self.courier} везёт заказ'

class PickupOrder(Order):
    def how_to_receive(self):
        return 'Заберите заказ в пиццерии'

orders = [
    DeliveryOrder('Маргарита', 'Ленина 5', 'Айбек'),
    PickupOrder('Пепперони', 'Мира 12'),
]

for order in orders:
    print(order.how_to_receive())
Разница коротко: переопределение — это когда каждый вид задаёт свой how_to_receive() (два прошлых слайда), а полиморфизм — когда один цикл вызывает его у разных заказов (этот слайд). Кстати, полиморфизм бывает и без наследования — достаточно, чтобы у объектов был метод, подходящий для одинакового вызова.
Один цикл обслуживает оба вида заказов — не надо проверять «а ты какой?».

ООП — код вокруг понятных сущностей

Вся история — про одни и те же заказы. Если узнаёшь их в каждой карточке — ты понял ООП.

1 · Объект
order1 — конкретная карточка: Маргарита, Ленина 5, готовится.
2 · Класс
Order — бланк: какие поля и действия есть у любого заказа.
3 · Наследование
DeliveryOrder(Order) — та же основа плюс courier.
4 · Полиморфизм
how_to_receive() — один вопрос, у каждого свой ответ.

ООП не гарантирует порядок сам по себе — аккуратный код можно писать и без него. Но объекты дают удобный способ: думать заказами, а не связями между десятками переменных.
